# DESIGN (design-grill target)

## Goal
Today each form hard-codes its menu (`const MENU = [...]`, + la_musa `CATEGORIES`/`VARIANT_ITEMS`/`HAS_PHOTO`) — a hand-maintained source. 1c-b3 makes the form render the **catalog-generated bundle** (1c-b1) instead, so a future catalog edit (the portal) reaches customers. **Byte-identical to today** (the bundle == the current MENU, proven in 1c-b1) — this is a SOURCE swap, not a menu change. After 1c-b3 the form is catalog-sourced; only 1d (pricing authoritative) remains before a portal edit is fully live.

## 🔑 THE CONSUMPTION MECHANISM — INLINE at build, in a SEPARATE `<script>`, validated (RESOLVED per design-grill — the mechanism is now specified, not punted)
INLINE-at-build is the availability-first choice (a committed generated artifact, ZERO runtime fetch — nothing to fail offline/CDN/RTDB-down). But the mechanism must be exact, or a bad splice IS production (Netlify deploys the committed HTML). Required:
- **🔒 The generated block is its OWN `<script>` that assigns a GLOBAL, never a bare `const MENU`.** A generator writes a separate script — `<script id="form-menu-bundle">window.__FORM_MENU_BUNDLE__ = {dishes:[...], categories:[...], variant_items:{...}, has_photo:[...], pickup_only_cats:[...], weekend_only_cats:[...]};</script>` (values via `JSON.stringify`, byte-stable). This is BEFORE the main form script. Because it's a SEPARATE script tag, a syntax error / half-written / empty generated block fails INDEPENDENTLY — the browser skips that one script and the main script still runs (and falls back). Two `const MENU = …` in one scope is invalid JS and is FORBIDDEN.
- **The main form script SELECTS + VALIDATES — PER consumed structure independently (re-grill should-fix), not just `dishes`:** rename today's hard-coded literals to `FALLBACK_MENU`/`FALLBACK_CATEGORIES`/`FALLBACK_VARIANT_ITEMS`/`FALLBACK_HAS_PHOTO`/`FALLBACK_PICKUP_ONLY`/`FALLBACK_WEEKEND_ONLY` (kept during EXPAND). Then a **per-structure validated select**: e.g. `const _b = window.__FORM_MENU_BUNDLE__ || {}; const MENU = (Array.isArray(_b.dishes) && _b.dishes.length && _b.dishes.every(d => d && d.id && d.name)) ? _b.dishes : FALLBACK_MENU;` and the SAME independent shape-check-then-fallback for `CATEGORIES` (array), `VARIANT_ITEMS` (object), `HAS_PHOTO` (→ `new Set(_okArray ? _b.has_photo : FALLBACK_HAS_PHOTO)`), `PICKUP_ONLY_CATS`, `WEEKEND_ONLY_CATS` (arrays). Each structure falls back on its OWN validity — a partial bundle can't leave one structure `undefined`. A malformed/absent/empty bundle → every select falls back → **menu always renders.**
- **🔒 The SPLICE mechanism (deterministic, atomic, reviewable) — the generator that writes the block into the form HTML:** (a) an **exactly-once BEGIN/END marker pair** in each form (`<!-- FORM-MENU-BUNDLE:BEGIN -->` … `:END`) delimiting ONLY the generated script — the generator ASSERTS exactly one begin + one end (else throw, never write); (b) it replaces ONLY between the markers (never touches surrounding form JS — hand-edits elsewhere are safe); (c) **atomic write** (temp file + rename); (d) **🔒 SCRIPT-SAFE serialization (re-grill blocking — `JSON.stringify` ALONE is NOT script-safe):** after `JSON.stringify`, **escape `<` → `<`** (`JSON.stringify(bundle).replace(/</g, '\\u003C')`). A menu string containing `</script>` would otherwise close the inline script in the HTML parser BEFORE any JS runs (and `<!--` / `-->` / the marker-comment string could corrupt script parsing or fool the marker count on the next regen). Escaping `<` neutralizes ALL of them — `</script>`, `<!--`, `-->`, and marker injection — while remaining valid JS/JSON (`<` parses as `<`). (e) **post-splice validation via an HTML PARSER, not JS eval:** load the written HTML through an HTML parser/DOM, extract the generated `<script>`'s global, assert it deep-equals the source bundle — this catches a `</script>` break that a raw JS-eval check would miss (the HTML parser is what closes the tag). (f) **idempotent** (re-running yields byte-identical HTML). The generator refuses to write on any assertion failure (fail-closed → the committed HTML never gets a bad splice).

## Testing
- **Splice validity + completeness (grill blocker #2):** after the generator writes the block, RE-PARSE the final form HTML's generated `<script>`, extract `window.__FORM_MENU_BUNDLE__`, and assert it deep-equals the source bundle (both brands) — proves the splice produced VALID, COMPLETE JS, never partial/corrupt. The generator throws (writes nothing) on a marker-count ≠ 1 or a validation failure.
- **🔒 Script-injection mutation (re-grill blocking — the load-bearing safety test):** run the generator with a dish `name`/`description` containing `</script><!-- FORM-MENU-BUNDLE:END --><script>alert(1)</script>` (and `<!--`/`-->`). Load the RESULTING form HTML through an **HTML parser / DOM** (not `eval`/`require` — the HTML parser is what a `</script>` breaks), and assert: the generated `<script>` is intact (the `<` escaped to `<`), the global parses + deep-equals the source (including the literal `</script>` inside the dish name), the marker count is still exactly one begin/one end (marker injection didn't fool the splice), and the menu renders the item with its literal name. Falsifiable: without the `<`-escape, this test fails (the HTML parser closes the script early).
- **Idempotence:** re-running the generator on the same catalog/bundle yields a **byte-identical** form HTML (diff-stable; the splice touches ONLY the marked region — surrounding form JS byte-unchanged).
- **DOM-load render parity (grill blocker #1/#2 — load the FINAL HTML, not just JSON):** load each built form HTML in a headless DOM, run its render, and assert the rendered menu (cards, categories, order, photos, prices) == the current hard-coded form's render, both brands. A JSON-only compare is insufficient — the splice must produce a form that actually LOADS + RENDERS.
- **Corrupt/empty generated block → fallback renders (availability-first, grill blocker #1):** with the generated `<script>` emptied, syntactically broken, or the global missing/malformed, the validated-select falls back to `FALLBACK_MENU` (during expand) OR degrades to empty-but-renders (post-contract) — the form JS still PARSES and LOADS (separate-script isolation), the page never blanks with a parse error.
- **86 overlay:** with a simulated `item_availability` (an id sold-out), the generated-MENU form greys + pills it exactly as today; with the availability read absent, the menu still renders (no-op).
- **Rewards picker + reorder:** `buildRedeemCatalog()` off the generated MENU == off the hard-coded MENU (both brands); reorder resolves items unchanged; eligibility == server eligibility.
- **Availability-first:** the menu renders with NO network at all (inline) — assert no runtime fetch is required for the menu to appear.
- **Expand fallback:** with the generated block absent/invalid, the form falls back to the hard-coded array (during expand) and still renders.
- Full existing form behavior unchanged; if there's a form test harness, it stays green.
