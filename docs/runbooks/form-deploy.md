# Order-form deploy — the baked menu must match the published catalog

Every customer order form ships a BAKED menu (`<script id="form-menu-bundle">`, generated by
`xpizza-functions/generate-form-bundle.mjs`) that is shown until the live menu arrives. If the baked
menu differs from what the brand has PUBLISHED in the merchant portal, a customer who adds a changed
dish before the live menu applies is blocked at checkout («Algunos productos de tu carrito
cambiaron»). This happened to la_musa from 2026-09-16 to 2026-10-25.

## Required before ANY push that deploys a form folder (every brand)

```
cd xpizza-functions && node tools/form-bundle-live-check.js
```

- It checks every form in `tools/splice-form-bundle.js` FORMS against that brand's live public menu
  (the URL the form itself fetches). A form folder that carries a baked menu but is not registered
  there also fails.
- **Exit 1 / `FAIL` lines** — a dish, option, variant group, category or photo flag that is in both
  menus but differs, or that is baked but no longer published. Do not deploy. Bring the brand's
  bootstrap data (the form `MENU`/`EXTRAS` literals and its `menu-pricing.js` row) in line with the
  published catalog, run `node generate-form-bundle.mjs`, regenerate (form-source-inventory, R3), and
  re-run this check.
- **`WARN` lines** — published-only additions. They cannot block a cart (they appear once the live
  menu applies); deploying is fine. Fold them into the bootstrap as their own follow-up.
- Identity keys (`identity_id`, `dish_id`, `extra_id`) are ignored: the forms accept-and-ignore them.

The comparison itself is unit-tested offline (`node tools/form-bundle-live-check.test.js`, in
`npm test`); the live run needs the network and so is a deploy step, not a test.
