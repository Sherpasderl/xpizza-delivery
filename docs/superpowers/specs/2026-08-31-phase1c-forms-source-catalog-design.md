Pizza, La Musa) AND future onboarded merchants** — with priorities **scalability · ease-of-use · aesthetics · robustness**. Together 1c+1d make "edit a menu" ONE operation (change catalog → publish → forms+KDS+pricing+POS regenerate coherently, with preview+rollback) — the ease-of-use + robustness foundation the P3 portal UI (where aesthetics live) sits on top of. **The arc is uniform across all restaurants by construction** (no Tier-1/Tier-2 special-casing in the catalog/pricing path) = the scalability requirement.

## Goal — collapse 4 hand-synced menu sources to 1 generated pipeline
Today the menu lives in 4 hand-synced places (form display array, `menu-pricing.js` prices, the catalog prices, the KDS manifest). 1c makes the **Firestore catalog (schema-v2) the single source of truth**, and **generates every consumer from it**: the order-form served menu bundle, the KDS manifest (`menus/{rid}.json`), and (at 1d) the server price tables + POS menu. Editing the menu becomes one operation; all surfaces regenerate coherently. This is the "menu is data" endgame and the substrate the P2/P3 merchant portal later writes to.

## Schema-v2 — a LOSSLESS FULL-MENU store (REVISED per codex design-grill 2026-08-31)
The grill found the form `MENU` is a structured document, not a flat item list — so a minimal "+5 display fields" schema is INCOMPLETE. Model it losslessly:
- **`menu_items/{docId}` = the item's COMPLETE form record**, verbatim: `{ key, price, name, description, cat, subcat, variantOf, choice, tags, emoji, color, img/has_photo, … }` — every field the form dish object carries, so the bundle regenerates **byte-identical by construction** and every behavior/variant/eligibility field survives.
- **A `menu_structure` doc** (or ordered category docs) carrying the **CATEGORIES: order, labels, subcats, layout** + the variant relationships (`VARIANT_ITEMS` — the Pad Thai protein variants) that the form renders.
- **🔒 GRILL-FIX #2 — `key` is the IMMUTABLE identity, `name` is a data field.** X. Pizza prices by NAME (`itemPricingKey`), so `key === name` for X. Pizza TODAY, but the schema treats `key` as the immutable pricing/order identity and `name` as display data — a rename is a **price-key + order-key migration, gated**, never a copy edit. Pin `key===name` for X. Pizza (or split `display_name`) with a guard test.
- **🔒 GRILL-FIX #5 — a SEPARATE display reader.** `getRestaurantDocs` stays the pricing reader (returns `{key,price}` only — the 1b path is BYTE-UNCHANGED, ignores the new fields, codex-CONFIRMED). Add a distinct `getRestaurantMenu` (full-record + structure) for the bundle generation. Two readers, one store.
- Extras stay `{key,price}`; **modifier/variant UI logic stays code (deferred)** — but the item FIELDS it keys off (`cat`, `subcat`, `variantOf`, `choice`, launcher config, per-category modifier maps — GRILL-FIX #7) travel in the lossless record, so the extras UI is unbroken.
- `profile` doc unchanged. Prices whole lempiras.

## Bootstrap (one-time) — extract today's menu INTO the catalog, parity-proven
The full item menu currently lives split across the form (display) + `menu-pricing.js` (price). One-time: extract each item's display from the form dish array + price from `menu-pricing.js` → seed the schema-v2 catalog. **Parity gate:** the seeded catalog's items must reproduce today's form array + `menu-pricing` prices byte-identically, both brands (a `menu-parity`-style + emulator round-trip proof). After bootstrap, the catalog is authoritative; the form array + `menu-pricing` become DERIVED/verified, not hand-edited.

## Generation — catalog → artifacts (retire the hand-sync)
A publish step generates, FROM a catalog version:
- **The form served menu bundle** — the dish array the form renders (name/desc/category/price/tags/photo-flag), committed/deployed with the form. Replaces the hard-coded array.
- **The KDS manifest** (`menus/{rid}.json`) — currently generated from the FORM (`build-menus.mjs`); re-point it to generate from the CATALOG (the new source). (Reconciles the [[menus-manifest-ci-cleanup]] direction: one source, generated artifacts, tests in CI.)
- (1d) the server `MENU_BY_RESTAURANT`/`EXTRA_PRICES` + POS `pos-menu.json` become catalog-derived too — deferred to 1d.

## Versioned-publish — IMMUTABLE snapshot + atomic pointer flip (REVISED — grill-fix #6)
The catalog is published as an **IMMUTABLE versioned snapshot**, and publish **flips a single `active_version` pointer LAST** (never mutate live per-item docs in place — the grill flagged that querying mutable docs mid-publish is an inconsistent-read hole). So: write all of version `N+1`'s docs under an immutable version namespace → verify → **atomically flip the `active_version` pointer** → readers/generation read the pointed-to version. Rollback = flip the pointer to a prior version (the old snapshot is retained). This is (a) the safe cutover primitive (the 1a "profile-last / no-live-reads" note flagged versioned-publish as the precondition for atomic cutover under a live reader), (b) the mechanism 1d needs to retire the code fallback, (c) the preview/rollback differentiator the incumbents lack (research 2026-08-31). Preview = generate-from-a-version dry-run, writes nothing.

- **⟲ PUBLISH-MECHANISM REQUIREMENTS the 1d money-cutover depends on (added per 1d codex grill 2026-08-30 — build the HOOKS here even though 1d populates the money-specific values):** (a) **each version record carries an expected item COUNT + a table HASH + a schema version** — so a reader can verify semantic completeness before serving, not just trust pointer-last (1d completeness-on-read); (b) **the fallback pricing snapshot is written in the SAME Firestore batch/transaction as the `active_version` pointer flip** (coherent by construction — two datastores can't be transactionally atomic, so the RTDB mirror is version-checked, never assumed coherent — 1d blocker #2); (c) **publish exposes a VALIDATION + BOUNDS + CONFIRMATION hook** the money layer fills in 1d (structural validity + max %/absolute delta vs active + per-category low-price floor + a fiscal-restaurant preflight preview of gross/taxable/ISV/rebaja); (d) **rollback re-emits the snapshot** to the rolled-to version in the same batch. These are the mechanism; 1d supplies the money/fiscal thresholds.
- **⭐ PREVIEW + ROLLBACK are FIRST-CLASS (portal-serving, owner 2026-08-30).** Because the portal edits a LIVE revenue surface uniformly across all restaurants, these are load-bearing operations the P3 editor calls directly, not internal conveniences: **Preview** = generate every artifact (form bundle + KDS manifest + the 1d pricing snapshot) from a *staged, not-yet-active* version and render/diff it, writing nothing to the active pointer — so an owner sees exactly what a publish would do before it goes live. **Rollback** = re-flip `active_version` to any retained prior version, a single atomic pointer write, no re-seed — so a bad edit is undone in one action. Retain the last N versions (N ≥ a few) so rollback has targets. Design the version-record so these are cheap pointer operations, never re-derivations of live per-item docs.

## Cutover — expand-contract on the LIVE forms (availability-FIRST)
Per the NY-split playbook ([[xpizza-ny-menu-split]]), zero-window:
1. **Expand:** the form reads the catalog-derived **bundle if present, else the existing hard-coded array** (fallback). Deploy (git-CD). Both present, byte-identical.
2. **Verify:** the bundle renders byte-identical to the hard-coded array in prod, both brands (the served menu, prices, categories, photos, and the existing **Agotado/86 overlay** — `item_availability` grey-out from KDS Phase 2b — all intact).
3. **Contract:** remove the hard-coded array; the bundle is the sole form menu source.
- **AVAILABILITY-FIRST:** the bundle is a **committed/deployed static artifact** (offline-safe — NO load-time Firestore fetch on the customer path), so the menu ALWAYS renders even if Firestore is slow/down. The existing RTDB `item_availability` 86 overlay stays layered on top (the fast real-time channel — matches the incumbent snapshot+overlay pattern).

## Money / availability posture (assert)
Display-only — the SERVER still re-prices from the catalog (1b), so a bundle error can NEVER mis-charge · **displayed == charged is NOT automatic from "one source"** (the static git-CD bundle and the server pointer cannot flip atomically — see 1d "Cross-surface activation coherence"); the binding guarantee is that the **server-authoritative total is shown at CHECKOUT-confirm before payment**, so a stale bundle can never charge more than the confirmed number · the form ALWAYS renders (static bundle + fallback during expand) · the 86 overlay + cart + checkout + payment flows BYTE-UNCHANGED · the 1b pricing path (menu_item `key`/`price` read) byte-unchanged · both forms byte-parallel where they already are.

## Downstream consumers of the form `MENU` — all must survive (grill-fix #8)
The form `MENU` array feeds more than rendering: the **rewards redemption picker** (`buildRedeemCatalog()` derives the eligible display from `MENU`) and the **reorder path**. When `MENU` becomes bundle-sourced, these read the same array → work unchanged — PROVIDED the bundle carries the same items+fields. **Pin the eligibility coherence:** the bundle's redemption-eligible items must still match the server-authoritative eligibility (X. Pizza static name allowlist / La Musa non-alcohol id derivation) — parity-gate it so a catalog menu change can't make the rewards picker diverge from what the server will honor.

## Testing
- **Bootstrap parity:** seeded schema-v2 catalog reproduces today's form array + `menu-pricing` prices byte-identical, both brands (emulator round-trip, non-vacuous sentinel).
- **🔒 Bundle parity — FULL object shape + order (grill-fix #4, load-bearing):** the catalog-generated bundle == the current hard-coded `MENU` **byte-identical incl. every field and order** — `tags`, `emoji`, `color`, `img`/photo, `cat`/`subcat`/`variantOf`/`choice`, category order, item order, La Musa variants/subcats/layout — both brands. A wrong/reordered bundle = wrong customer menu.
- **Two readers:** the pricing reader (`getRestaurantDocs` → `{key,price}`) is BYTE-UNCHANGED (1b path); the new display reader (`getRestaurantMenu`) round-trips the full record + structure.
- **name===key guard (X. Pizza):** a test that the X. Pizza item `key` equals its `name` (rename = gated migration, not a silent price-key change).
- **Rewards picker + reorder:** `buildRedeemCatalog()` and reorder produce the same result off the bundle as off the hard-coded array; bundle eligibility == server eligibility (parity-gated).
- **KDS manifest from catalog** == the current form-generated manifest (no KDS regression), golden in CI ([[menus-manifest-ci-cleanup]]).
- **Availability-first:** the form renders from the bundle with NO Firestore fetch; the 86/Agotado overlay still greys `item_availability` items (keys off `name` x_pizza / `id` la_musa).
- **Versioned-publish:** immutable snapshot + atomic pointer flip; generate-from-version deterministic; rollback = flip to prior version; preview writes nothing.
- Full `npm test` EXIT 0; the 1b pricing tests + factura tests UNCHANGED.
