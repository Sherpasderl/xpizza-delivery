Merchant portal: the notice while Sherpa updates a menu

What happened on 2026-11-02. Sherpa ran a server-side menu migration that wrote display fields (section badge order, reward icons, a dish's extras policy) into restaurants' saved drafts before the live menu had them. The portal then saw a draft it could not publish and, exactly as it does for a merchant's own broken draft, offered «Volver al menú publicado»; the owner clicked it, and that silently discarded Sherpa's changes, which the portal cannot even display.

The approved fix. The server flags such a draft (platform_changes_pending) and refuses a merchant reset of it. The portal only stops offering the reset and shows a calm notice instead. Sherpa resolves it from its side: it publishes the update, and the draft becomes publishable again. Nothing on these screens is a new control; the merchant has nothing to do.

Every frame below is drawn by the real portal: its own stylesheet, its Archivo font and its page markup, at 1280 px and 390 px, light and dark. Only the notice and the panel are added on top.

Sample data. «Pizzería Del Valle», its sections, dishes and prices, the owner's e-mail and the branch count are examples, not a real brand. All Spanish copy on these screens is a proposal for the owner's approval (Q2 below).

N2 · After: the refusal panel, if a reset still reaches the server

409 platform_changes_pending

If a reset ever reaches the server in this state (a second tab, a stale page, a direct call), the server answers 409 platform_changes_pending and writes nothing and the portal shows it in the review modal with the same panel renderer as every other refusal (renderOutcome: icon, title, detail, one action). This one uses the info icon rather than the warning: nothing went wrong on the merchant's side. The single action «Entendido» closes the panel; it does not reset, retry or reload.

What changed, and what did not

  • The server is the authority. It flags the draft and refuses a merchant reset of it (409 platform_changes_pending). The portal only stops offering the reset and tells the merchant why; it never decides on its own whether a draft is Sherpa's.
  • No regression. A merchant's own unpublishable draft (a removed product, a structure change) still gets today's red box and «Volver al menú publicado», exactly as in A0, and the existing refusal panels (for example «Tu borrador no coincide con el menú publicado») are untouched. Only the server-flagged case takes the new path.
  • Nothing for the merchant to do. Sherpa publishes the update from its side; the draft then becomes publishable again and the notice goes away on the next load. Price changes needed before that go through Sherpa («escribinos»).
  • No new look. The notice is the portal's existing quiet callout; the panel is the existing panel renderer with the existing info icon; the disabled states are the ones the stylesheet already has.

Questions for the owner

Q1 · Should the notice name what Sherpa is changing?As drawn it stays generic («cómo se ve tu menú»). It could instead list the fields, for example «íconos de recompensas, orden de etiquetas». Naming them is more informative but the list would change with every migration; generic copy needs no upkeep.
Q2 · The copy is a proposal. The notice title and body, the review-bar line «Publicar se habilita cuando Sherpa termine.», the panel's title, detail and «Entendido», and the header lock's «Solo lectura» line are all for your approval.
